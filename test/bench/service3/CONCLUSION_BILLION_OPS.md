# CONC 亿级请求承载能力结论

> 承接「压测 kaula 的 CONC 能不能抗住亿级请求服务」。
> 本轮修复两处内存泄漏后给出**确定性结论**与**外推依据**。
>
> 环境：32 核 AMD EPYC 9K84 / 123 GiB RAM / Linux 6.6.117，
> `SVC_WORKERS=4`（与 Go 对照边同配置），100 并发连接闭环。

## 1. 结论

**修复合计 ≈240 B/请求的两处内存泄漏后，CONC 服务的内存占用与请求数
完全解耦 —— 可承载亿级（乃至更高）请求而不 OOM。**

判据是 **`rss_per_req_b`**（每请求 RSS 增量）：

| 版本 | `rss_per_req_b` | 1 亿请求外推 RSS 增量 |
|---|---|---|
| 修复前 | 49.23 B/req（libc 泄漏）<br>+ 184–197 B/req（KMM 泄漏，早轮次） | **≈ 4.7 GB ~ 23 GB** → 必然 OOM |
| 修复后 | **0.15 B/req** | **≈ 15 MB**（常数级，非累积） |

> 修复后 `0.15 B/req` 已进入**测量噪声底**（两轮 0.15 / 0.16，
> ΔRSS 恒为 0.5 MB 且不随请求数变化）。阶梯 360s 的 19,884,807
> 请求实测 **ΔRSS = 0.0 MB**，比 2 轮 60s 更干净——增量是启动期
> 一次性开销，不是按请求累积。

## 2. 证据链

### 2.1 阶梯压测（请求数递增，ΔRSS 恒零）

| 时长 | 请求数 | ΔRSS | B/req |
|---|---|---|---|
| 120s | 6,553,893 | 0.0 MB | 0.0000 |
| 240s | 13,329,459 | 0.0 MB | 0.0000 |
| 360s | **19,884,807** | **0.0 MB** | **0.0000** |

请求数从 650 万涨到 1990 万（**3 倍**），ΔRSS 恒定 0 —— 内存与请求数
彻底解耦。

### 2.2 连接数扫描（连接数递增，ΔRSS 恒零）

| 并发连接 | 请求数 | ΔRSS | B/req |
|---|---|---|---|
| 100 | 3,311,264 | 0.0 MB | 0.0000 |
| 1000 | 3,612,922 | 0.0 MB | 0.0000 |
| 4096 | 3,370,210 | 0.0 MB | 0.0000 |

泄漏与连接数同样解耦。

### 2.3 分段归因（证明泄漏已归零而非被掩盖）

运行期探针周期性采样各段用量：

| 段 | 修复前 | 修复后 |
|---|---|---|
| KMM `slab_alloc` / `sv_usage` | 恒定 64000 | 恒定 64000（本就健康） |
| `scope_depth` | 恒定 0 | 恒定 0 |
| **libc `uord`** | 3.3 MB → **236.4 MB** | 229,648 → **225,952 B**（零增长） |
| **`rss`** | 200.8 → **422.1 MB** | **197.7 MB 恒定** |

## 3. 性能对照（Kaula CONC vs Go）

同配置、同负载、同口径（RTT 由 loadgen 侧测，mismatch 逐位校验）：

| 指标 | Kaula CONC | Go | 比值 |
|---|---|---|---|
| TPS | 56,481 / 56,074 | 81,416 / 79,816 | 0.70× |
| p50 | 398 / 402 µs | 424 / 430 µs | **0.93×（更优）** |
| p99 | 69.5 ms | 57.8 ms | 1.20× |
| p999 | 73.4 ms | 65.0 ms | 1.13× |
| `rss_per_req_b` | **0.15** | 1.15–1.34 | **0.12×（更优）** |
| `minflt` | **127** | 3,542–6,875 | **0.027×（更优 36 倍）** |
| 用户态 CPU | 95.9% | 96.1% | 持平 |
| 系统态 CPU | **83.8%** | 56.0% | 1.50× |

**要点**：

- **正确性**：全程 `mismatch=0`、`errors=0`（100/1000 连接）。
- **内存效率**：Kaula 的 `minflt` 比 Go 低 **36 倍**，`rss_per_req_b`
  低 **8 倍** —— CONC 的 KMM scoped allocator + 有栈协程在内存足迹上
  显著优于 Go 的 GC 堆。
- **延迟**：p50 优于 Go；p99/p999 落后（**系统态 CPU 1.5×** 是主因，
  指向 epoll 事件循环与 Worker 间的跨线程协调开销）。
- **吞吐**：落后 Go 约 30%，属已知的 IoDriver 单线程分派税。

## 4. 剩余风险与后续方向

| 项 | 状态 | 说明 |
|---|---|---|
| 内存泄漏 | **已消除** | 两处独立泄漏均修复并加回归锁 |
| 4096 连接下 `errors>0` | **非缺陷（压测器收尾假阳性）** | 全部为 `err_timeout`（1536）、`err_eof=0`、`mismatch=0`；`loadgen.go:189` 已注明这是收尾语义造成的假阳性，服务始终存活 |
| p99/p999 落后 Go | 已知 | 系统态 CPU 偏高，IoDriver 分派路径有优化空间 |
| 吞吐落后 Go 30% | 已知 | 见 `REPORT_60K.md` 的 IoDriver 排队改造结论 |

### 亿级能力的工程含义

「抗住亿级请求」有两种解读，本基准覆盖后者：

1. **峰值瞬时**：亿级 QPS —— 受单机网卡/内核网络栈上限约束，
   任何单进程实现都不现实，需水平扩展（瓶颈不在 CONC）。
2. **累计总量**：**亿级请求量的长期服务** —— **CONC 已满足**：
   稳态内存占用 O(1)，不随时间累积。

以实测 56k TPS 计，1 亿请求 ≈ 30 分钟持续压测。修复前会在这 30 分钟
内泄漏 ~4.7 GB；修复后 RSS 保持恒定。
