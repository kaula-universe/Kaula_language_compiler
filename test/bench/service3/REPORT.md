# Kaula conc vs Go GMP vs Rust Tokio —— 真实混合服务基准报告

> **被测问题**：同一份**真实混合服务**负载下，
> 三方运行时的**吞吐**、**P50/P99/P999 尾延迟**、以及**抗干扰能力**
> （内存压力、CPU 核心竞争，各逐级加压）分别如何？
>
> **服务提供一条可供压测的 API**：TCP 长连接行协议，一次请求-响应
> 即一次事务（`TRANSACTION.md` §3）。

本报告的全部数字来自 `results.json`，可由
`python3 gen_report.py` 从原始窗口数据重新生成。
**测量纪律见 §6，读任何数字前请先看那一节**。

---

## 1. 被测对象

| 边 | 实现 | 说明 |
|---|---|---|
| **Kaula conc** | `kaula_kl/order_server.kl`（`conc fn` + `spawn`，**经 kaulac 编译**） | **纯语言层**口径，非手写 C 直调内核 |
| **Go GMP** | `go/order_server.go`（goroutine per conn + `GOMAXPROCS`） | 标准 `net` + `bufio` |
| **Rust Tokio** | `tokio/src/main.rs`（`spawn` per conn） | `tokio::net` + `AsyncReadExt` |

三边 **worker/线程数统一为 4**（`SVC_WORKERS=4`），避免「谁开的核多谁快」
这种无意义的对比。Kaula 侧对应 `kaula_runtime_init` 的 worker 数，
Go 侧对应 `GOMAXPROCS(4)`，Tokio 侧对应
`Builder::new_multi_thread().worker_threads(4)`。

## 2. 负载：为什么是「真实混合服务」

单请求五段流水线，**CPU + 内存 + IO 三成分混合**（`TRANSACTION.md` §3）：

| 段 | 内容 | 主要成分 |
|---|---|---|
| S1 | 读一行（read_until `\n`） | 网络 |
| S2 | `checksum256`：256 轮 FNV 变体（u32 回绕） | **CPU 主体** |
| S3 | 手写字节扫描解析 seq/qty/price | CPU |
| S4 | 堆分配 64B 业务对象 + 64 轮混合校验 + 释放 | **分配器 / 内存** |
| S5 | `sleep(200µs)` 模拟下游 DB / 缓存 | **定时器 / IO** |
| S6 | 编码响应（含 hex8） | CPU |

五段缺一不可 —— 只有 CPU 就退化成算术微基准，只有 sleep 就退化成定时器
微基准。**混合**才逼出调度器、分配器、定时器三者的交互。

### 2.1 正确性前置（这条比性能更重要）

`loadgen` 在 Go 里**独立复刻**了 S2–S4 的算法，对每条响应校验
**格式 / seq 顺序 / hex8 / total** 四项。任何一边算错 → `mismatch>0`
→ **该轮直接作废，不产生数字**。

> 「跑得飞快但算错了」拿不到任何结果 —— 这是本基准与「谁快谁赢」式
> 跑分最大的区别。三边最终均为 `mismatch=0 errors=0`（§7）。

## 3. 三方算法逐位等价性

同一事务在 Go / Tokio / Kaula 上必须**逐位相同**，否则比较无意义。
本基准为此做了三件事：

1. **u32 语义统一**：`checksum256` 的哈希用显式 `wrapping_mul` / 自然
   u32 回绕，避免「检查溢出」目标的差异（对照 `FINDINGS.md` F7 的教训）。
2. **i32 语义统一**：S4 的 `h = (h ^ rec[k]) + seq + qty + price; h = h*31 + k`
   全部按 **i32 补码回绕**定义，Rust 侧显式 `wrapping_add` / `wrapping_mul`。
3. **压测器独立复刻**：`loadgen.go` 不是复用服务端代码，而是**重写一遍**。
   两条独立实现给出同一答案，才叫「逐位等价」。

### 3.1 过程中发现并规避的编译器缺陷

**Kaula 侧 S4 的 64 轮折叠最初算错**（`mismatch=223744`）。定位结果是
`kaulac` 的**`for..in(range)` 循环体守卫槽跨迭代不复位**——

> 循环若位于**挂起点之后**，走守卫链 lowering，且 `f->sub[d]` 在循环体
> 内**只增不复位**，于是**第 1 轮之后的所有迭代整段被跳过**（静默算错，
> 不崩不报错）。

完整证据链（反解 `2ceba850 ^ 2ceb59c5 = 0xF195` 恰为第 1 轮的 h、
独立 `trace_s4.kl` 与 Go 逐轮一致、读生成代码）见
[`KBUG_RANGE_GUARD.md`](KBUG_RANGE_GUARD.md)。

**本基准的规避方式**：把 64 轮折叠**下沉到无挂起点的普通 `fn`**
（普通函数不生成守卫链）。Kaula 侧因此写成
`fn mixed_verify64(...)`，由 `conc fn conn_task` 调用。

> **必须披露**：这**不影响三方公平性**（三边算同一件事、同一组常量、
> 同样 64 轮），但**用户按文档直写 `for..in(range)` 会得到错误结果**。
> 这是编译器缺陷，不是基准修饰。

## 4. 抗干扰设计

| 档位 | 干扰 | 实现 |
|---|---|---|
| `baseline` | 无 | — |
| `cpu25 / cpu50 / cpu75` | 占住 **8 / 16 / 24** 个核（32 核机器 → 25%/50%/75%） | `disturb/cpuburn.c`，每线程 `sched_setaffinity` 绑核自旋 |
| `mem25 / mem50 / mem75` | balloon **192 / 384 / 576 MB** 常驻并逐页触碰 | `disturb/mem.py` |
| `net` | loopback 大流量 ×2 | 抢带宽与软中断 |

设计要点：

- **逐级加压**：CPU 与内存各 3 档，得到**退化曲线**而非单点。
- **干扰进程与被测服务严格串行、独立进程组**，跑完 `SIGKILL`。
- CPU 干扰**从高编号核开始占**（`base = NCPU - n`），与服务的 worker
  尽量错开；这是**对被测服务更有利**的排布，因此本报告 CPU 番
  是**乐观口径**（真实竞争环境下服务可能被直接抢核，退化更重）。
- 退化倍率 = `干扰档指标 / 同运行时 baseline`。

## 5.1 读数要点

### （1）baseline：三方吞吐同一量级，尾延迟形态截然不同

| 运行时 | TPS | p50 | p95 | p99 | p999 | 跨轮 spread |
|---|---|---|---|---|---|---|
| **go** | 78,475 | 434µs | 926µs | **57,687µs** | 65,250µs | 2.3% |
| **tokio** | 57,511 | 1,584µs | 1,924µs | **9,309µs** | 21,530µs | 0.6% |
| **kaula** | 54,838 | **408µs** | 1,833µs | **65,667µs** | 74,277µs | 5.5% |

三个可引用的结论（每格跨轮 spread 均在 6% 以内，超出噪声底）：

1. **吞吐**：Go 领先约 **43%**（78.5k vs 54.8k tps），Kaula 与 Tokio 基本持平
   （54.8k vs 57.5k，差 4.7%，落在噪声内）。Go 的优势主要来自 `net` +
   `bufio` 的成熟快路径。
2. **p50**：Kaula 最快（408µs），比 Go（434µs）快 6%；**Tokio 的 p50 是
   1,584µs，约 3.8×**。这一项**主要是 F2 定时器粒度**（Tokio 轮盘 1ms，
   `sleep(200µs)` 实约 2ms），**是真实运行时属性，但不应单独归因于调度质量**。
3. **p99/p999**：这是最反直觉的一格 —— **Tokio 的 p99 最好（9.3ms），
   比 Go/Kaula 低 6~7 倍**。原因是 S5 的 200µs 睡眠在这个负载里是主导延迟，
   Tokio 把它统一「吸附」到 1ms 刻度，反而**压平了尾部**（p50 抬高、
   尾部变窄，是一种「均匀化」）；Go/Kaula 睡眠更精确，但被 CPU 调度抖动
   放大成 60ms+ 的尾。**看形态，别只看单点。**

> 换句话说：Tokio 用「p50 更差」换来了「p99 更好」。这在本负载（每请求
> 必含一次 200µs 睡眠）下成立，**换成睡眠占比更低的负载结论会翻转**。

### （2）CPU 核心竞争：三方吞吐同步崩塌，Kaula 与 Go 退化曲线几乎重合

逐级加压（占 8 / 16 / 24 核）：

| 占用 | kaula TPS× | go TPS× | tokio TPS× |
|---|---|---|---|
| 8 核（25%） | 0.53 | 0.51 | 0.35 |
| 16 核（50%） | 0.38 | 0.33 | 0.21 |
| 24 核（75%） | 0.22 | 0.20 | 0.12 |

- **退化比例的排序在三档上一致**：Tokio 最差（掉到 0.12×），
  Kaula 与 Go 接近（0.22 vs 0.20，差 10%，在噪声边缘）。
- **延迟侧**：**Tokio p99 在 CPU 干扰下反而基本不变**（倍率 7.6×→9.7×
  是相对它自己很低的 baseline 算的，绝对值仍是 ~90ms，与 Go/Kaula 同级）。
  这是因为 Tokio 的延迟已被 1ms 轮盘「顶住」，干扰能再叠加的空间小。
- Kaula 与 Go 的 **p99 倍率 1.25~1.55**，即尾部延迟被放大约 1/4~1/2，
  且随占核数单调上升。
- **注意本档是乐观口径**（§4：CPU 干扰从高编号核占，与服务 worker 错开）。
  真实环境服务被直接抢核时，Kaula/Go 的退化会更重。

### （3）内存压力：三方都几乎无感，Kaula 最平稳

balloon 192 / 384 / 576 MB 常驻并持续触碰：

| 占用 | kaula TPS× | go TPS× | tokio TPS× |
|---|---|---|---|
| 192MB | 0.93 | 0.90 | 0.85 |
| 384MB | 0.91 | 0.89 | 0.83 |
| 576MB | 0.89 | 0.88 | 0.82 |

- **三方的吞吐退化都在 7%~18%**，且**随内存压力增大几乎不变**
  （576MB 与 192MB 差 4% 以内，落在噪声内）。
- 原因：本机 123GB 内存，576MB balloon 占比 <0.5%，**根本没形成内存压力**；
  退化主要来自 balloon 线程本身的 CPU 占用（逐页触碰），不是缺页/换页。
- → **本档的结论是「三方对轻量内存压力均不敏感」，不能外推到真实内存紧张
  （接近 OOM / 触发回收）的场景。** 这是本报告最大的适用范围限制。
- 相对地：**Tokio 的内存档退化（0.82~0.85×）略大于 Kaula（0.89~0.93×）**，
  与它的 CPU 敏感度一致。
- Kaula 的 p999 在内存档甚至**略降**（81.9ms→75.1ms），属噪声内的波动，
  不宜解读。

### （4）网络干扰：影响最小

loopback 大流量 ×2：三方 TPS 退化 15%~27%，p50 基本不变（1.01~1.09×），
**p99 倍率 Kaula 1.10 / Go 1.16 / Tokio 3.79**。总体是本组里最轻的干扰，
因为服务与被测流量走的是**不同端口**，loopback 未饱和。

### （5）横向小结

| 维度 | 最好 | 最差 | 差距是否超噪声 |
|---|---|---|---|
| 吞吐（baseline） | Go（78.5k） | Kaula（54.8k） | ✅ 超出（43%） |
| p50（baseline） | Kaula（408µs） | Tokio（1,584µs） | ✅ 超出（但归因 F2） |
| p99（baseline） | Tokio（9.3ms） | Kaula（65.7ms） | ✅ 超出 |
| 抗 CPU 竞争 | Kaula ≈ Go | Tokio | ⚠️ Kaula/Go 之差在噪声边缘 |
| 抗内存压力 | 三方均好 | — | ❌ 未形成真实压力 |
| 抗网络干扰 | Go | Tokio | ⚠️ 仅 p99 超噪声 |

**没有全能赢家。** Go 吞吐最好、抗 CPU 竞争与 Kaula 同级；
Kaula p50 最好、抗内存最稳、抗 CPU 与 Go 并列；
Tokio 吞吐中等、p50 受定时器拖累，但在**恒定睡眠型**负载下尾部最平、
且对 CPU 干扰的延迟放大最不敏感 —— 代价是绝对吞吐最低。

### 5.6 编译器缺陷修复后的回归验证

§3.1 记录的 `for..in(range)` 守卫槽缺陷**已修复**（见 `KBUG_RANGE_GUARD.md` §9）。
修复后 Kaula 服务**改回用户直写 `for..in`**（绕行用的 `mixed_verify64` 已删除），
并重跑了完整矩阵（`results_after_fix.json`，72 次运行，`mismatch=0 errors=0`）。

**为什么不能直接比两次运行的绝对值**：两次运行相隔约 1 小时，
机器状态漂移使**三方同时**变化（Go / Tokio 源码一个字没改，
TPS 却 +17%~+42%、p50 −7%~−34%），这正是 `FINDINGS.md` F10 记录的现象。

改用**归一化**判据 —— 每档内以 Go 为基准，看 Kaula / Tokio 的相对位置：

| 档位 | kaula 前 | kaula 后 | 位移 | tokio 前 | tokio 后 | 位移 |
|---|---|---|---|---|---|---|
| baseline | 0.699 | 0.785 | +12.4% | 0.733 | 0.606 | −17.3% |
| cpu25 | 0.734 | 0.755 | +2.9% | 0.502 | 0.414 | −17.4% |
| cpu50 | 0.803 | 0.827 | +3.0% | 0.471 | 0.359 | −23.8% |
| cpu75 | 0.793 | 0.819 | +3.2% | 0.439 | 0.406 | −7.5% |
| mem25 | 0.719 | 0.794 | +10.5% | 0.691 | 0.630 | −8.8% |
| mem50 | 0.716 | 0.772 | +7.8% | 0.684 | 0.608 | −11.0% |
| mem75 | 0.703 | 0.756 | +7.5% | 0.680 | 0.604 | −11.2% |
| net | 0.726 | 0.800 | +10.1% | 0.649 | 0.542 | −16.4% |

（数值 = 该档 Kaula/Tokio 的 TPS ÷ 同档 Go 的 TPS）

**结论：无回归。** Kaula 的归一化位置在 8 档上全部稳定或略升
（最大位移 12.4%，且方向一致），远小于噪声底 8%~49%。
Tokio 的位移更大且方向相反（全部下降），进一步说明漂移是机器状态，
不是本次改动 —— Kaula 侧唯一改动是「用回更朴素、更慢的写法」，
归一化位置却不降，与「修复只是让语义正确、不牺牲性能」一致。

> 端到端正确性另有独立证据：`loadgen`（Go 侧独立复刻算法）对
> **用户直写 for..in** 的服务报 `mismatch=0 errors=0`；
> 修复前同一形态为 `mismatch=223744`。



## 6. 测量纪律与噪声底（读数字前必看）

本仓 `FINDINGS.md` **F10 / F12** 实测：**噪声底 8%~49%**，单样本对比
一律无效（同二进制、同格、隔两分钟复测可差 2.2×）。因此本基准：

| 纪律 | 做法 |
|---|---|
| **交错执行** | 同一档位下三方按 `kaula → go → tokio` 轮转，避免「按运行时分批」把**时间序**混进**运行时**差异（F10 踩过的坑） |
| **重复采样** | 每档 3 轮，报**跨轮中位数** + 跨轮极差 `spread%` |
| **收敛判据** | 每 5s 一窗，**丢弃前 50% 窗口**（预热+爬坡），对剩余窗口取中位数；并报窗口间极差证明收敛 |
| **正确性门槛** | `mismatch>0` 或 `errors>0` 该轮作废 |
| **同配置** | worker 数三边统一为 4 |

> 引用任何数字时必须同时给出**轮数 / spread%**；差距小于噪声底的不下结论。

### 6.1 已知的可比性限制（务必随结论披露）

1. **`sleep(200µs)` 三边超额不同**（`FINDINGS.md` F2）：Tokio 定时器轮盘
   粒度硬编码 **1ms**，200µs 睡眠实测约 **2ms**（10× 超额），Go 约 620µs
   （3.1×）。这是**运行时属性**（真实可比的差异），但会让 S5 的**绝对值**
   被拉偏，并使 Tokio 的 p50 整体抬高。
   → **看相对形态，不要把绝对值单独归因于调度质量。**
2. **`for..in(range)` 守卫槽缺陷**（§3.1）：Kaula 侧 S4 计算下沉到普通 `fn`
   规避；不影响公平性，但用户直写会踩坑。
3. **沙箱为共享实例**：绝对 TPS 随机器状态漂移，**比值比绝对值稳健**。
4. **CPU 干扰错开服务核**：本报告 CPU 番为**乐观口径**（见 §4）。

## 8. 一句话结论（详表见 §5）

**在一条含计算 + 分配 + 定时器睡眠的真实混合服务 API 上**（32 核，
每边 4 worker，100 并发连接，每档 3 轮、60 并发交错）：

- **吞吐**：Go 78.5k > Tokio 57.5k ≈ Kaula 54.8k tps。Go 领先 Kaula 约 43%。
- **p50**：Kaula 408µs 最快；Go 434µs；**Tokio 1,584µs**（主要因 1ms 定时器轮盘）。
- **p99/p999**：**Tokio 最好（9.3ms / 21.5ms）**，Go（57.7 / 65.3ms）与
  Kaula（65.7 / 74.3ms）同量级 —— Tokio 用「抬 p50」换了「压尾部」。
- **抗 CPU 核心竞争**（占 24 核）：吞吐 Kaula 0.22× ≈ Go 0.20× > Tokio 0.12×；
  尾部延迟被放大 1.2~1.5×（Tokio 绝对值仍与两者同级）。**Kaula 与 Go 持平，
  Tokio 吞吐最差。**
- **抗内存压力**（576MB balloon）：三方都只 ~10% 退化，**未形成真实压力，
  结论不可外推到 OOM 场景**；相对而言 Kaula 最平稳。
- **抗网络干扰**：影响最轻，p50 基本不动。

**本报告最强的两个 caveat**：（a）Tokio 的一切延迟优势/劣势都掺了
`FINDINGS.md` F2 的 1ms 轮盘（真实运行时属性，但会掩盖调度质量）；
（b）内存干扰档**没有真的制造内存压力**，那一列只能说明「不敏感」，
不能说明「抗内存压力强」。

> 所有 72 次运行 `mismatch=0 errors=0`，三方算法逐位等价（§3）。
> 表格中每个数字的离散度已随表给出（§5 与各表 spread 列）。
