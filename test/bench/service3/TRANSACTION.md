# 三方真实服务压测 —— 事务定义与公平性契约

> 本文档定义「真实混合服务」的**唯一负载语义**。Kaula(kl) / Go / Tokio
> 三边实现必须逐位等价，任何不一致都会污染 TPS 与延迟分位。
> 前身：`test/bench/TRANSACTION.md`（内核微基准）。本文件是**服务级**契约。

## 1. 为什么另起一套（与前身的关系）

`test/bench/` 已有的是**内核微基准**（`spawn`/`await` 闭包事务，无网络）。
本轮要回答的是**服务级**问题：真实混合服务在持续压力下的吞吐与尾延迟，
以及受干扰时的退化。差别决定了契约必须重写：

| 维度 | 内核微基准 | 本服务基准 |
|---|---|---|
| 入口 | 进程内 spawn 循环 | **TCP 长连接**、请求-响应 |
| 时间口径 | 内核打点 submit→complete | **客户端 RTT**（用户实际感知） |
| 并发 | 并发句柄窗口 | **并发连接数** |
| 干扰 | 无 | 内存/CPU核竞争/网络，逐级加压 |

**客户端 RTT 是唯一公平口径**：三边的服务端各自有不同的内核打点能力
（Kaula 有 EBR/预算计数器、Go 有 runtime/metrics、Tokio 有 task hooks），
用各自的内部计时必然不可比。RTT 由**同一个压测器**在三边之外测量。

## 2. 协议

行协议，UTF-8/ASCII，`\n` 结尾。

```
请求： O,<seq>,<item>,<qty>,<price>\n
响应： R,<seq>,<hex8 checksum>,<total>\n
```

- `<seq>`：客户端单调递增序号（从 1 起）。
- `<item>`：字母串（固定 `itemA`，服务端只跳过不解析）。
- `<qty>`,`<price>`：十进制整数（固定 `3`,`1990`）。
- `<hex8 checksum>`：**8 位小写十六进制**，不足补前导 0。
- `<total>`：`qty * price` 的十进制。

**响应必须严格按请求顺序回**（长连接上串行处理，不流水线）。

## 3. 每请求流水线（五段，三边逐段等价）

| 段 | 语义 | 说明 |
|---|---|---|
| **S1** | 读取一行（不含 `\n`） | 记录字节长度 `n` |
| **S2** | `checksum = checksum256(line, n)` | 见 §3.1，**CPU 主体** |
| **S3** | 解析 `seq` / `qty` / `price` | 手写十进制扫描，**不用 `strtol`/`Atoi`** |
| **S4** | 业务对象：分配 → 填充 → 64 轮混合校验 → 释放 | **内存成分**，见 §3.2 |
| **S5** | `sleep(200µs)` | **IO 成分**，模拟下游 DB/缓存 |
| **S6** | 编码响应并写回 | 含 hex8 转换 |

### 3.1 checksum256（S2）

```
h = 0x811C9DC5
for round in 0..256:
    for i in 0..n:
        h = (h ^ line[i]) * 16777619 + round      // u32 运算
return h
```

- **u32 回绕**是语义的一部分（FNV-1a 变体）。三边都用 32 位无符号运算，
  Go `uint32` / Rust `u32` 原生回绕，Kaula 用 `as<u32>` 显式转换。
  **不能用 64 位再截断** —— 中间 64 位乘法会改变低位以外的进位传播。
- 这是纯 CPU 段，24 字节行 × 256 轮 ≈ 6144 次内层迭代。

### 3.2 业务对象与混合校验（S4）

```
rec.qty   = qty
rec.price = price
h = 0
for k in 0..64:
    h = (h ^ rec_byte[k % size]) + seq + qty + price
    h = h * 31 + k
checksum ^= (u32)h
```

- Kaula 用 `kmm_v4_alloc(64)` 分配 64 字节并逐字节填。
- Go 用 `[64]byte` 数组并在**堆上**分配到 `*BizRecord`（`escape` 到堆）。
- Tokio 用 `Box<[u8; 64]>`。
- **三边都必须真的分配**：这段是为了让分配器/回收器进入每请求热路径。
  Go 的 GC、Kaula 的 KMM、Tokio 的 malloc 在这里正面相遇。
- `h` 用 **i32** 运算（三边同）。`h*31+k` 在 64 轮后会溢出 i32 ——
  三边的溢出语义必须一致：Go i32 原生回绕（`int32`）、Rust 必须
  `wrapping_mul`/`wrapping_add`、Kaula 用 `as<i32>` 显式截断。
  **这是最容易写出三边不等价的地方**，hex8 一致性检查就是为了抓它。

### 3.3 sleep（S5）

| 运行时 | 原语 | 契约 |
|---|---|---|
| Kaula | `std.time.time_sleep_us(200)` | `conc fn` 内 → IoDriver 定时器挂起 |
| Go | `time.Sleep(200 * time.Microsecond)` | 运行时定时器 |
| Tokio | `tokio::time::sleep(Duration::from_micros(200))` | 定时器轮盘 |

> **已知且必须随报告披露的不可比项**（`FINDINGS.md` F2 实测，Windows）：
> 三边 sleep 的实际超额不同 —— Go 3.1×、裸线程 4.9×、**Tokio 10×**
> （其轮盘粒度硬编码 1ms）。**Linux 上本轮重测**，数字见报告。
> 这条属于「运行时属性」，不是口径错误；但 `suspend` 类负载的
> 绝对值会因此被拉偏，**看相对形态而非绝对值**。

## 4. 正确性校验（三边必须逐位一致）

压测器对每条响应校验：
1. 格式合法（`R,<seq>,<hex8>,<total>`）；
2. `seq` 与请求一致（顺序性）；
3. `total == qty*price`；
4. **`hex8` 与压测器本地独立算出的期望值一致**。

压测器在 Go 里**独立复刻**了 §3.1–§3.2 的算法（`expected_checksum`）。
任何一边算错 → `mismatch` 计数增长 → 该边数据作废（跑多快都没意义）。

> 这是前身 `F7` 的教训：跨语言基准里任何算术都要先问「三边溢出语义是否一致」，
> 且必须有一条**独立于被测方**的校验通路。

## 5. 测量口径

- **TPS**：`窗口内完成的请求数 / 窗口秒数`。预热期不计。
- **延迟分位**：客户端单请求 RTT（发请求 → 收到完整响应行），
  分位下标 `(n*p)/100`，`p999` 用 `/1000`，夹到 `n-1`。
- **收敛**：每 5s 一个窗口，丢弃前 50% 窗口（含预热与爬坡），
  对剩余窗口取**中位数**。单窗口数字不单独引用。
- **干扰对照**：同一服务、同一并发、同一时长，只切换干扰档位；
  退化倍率 = `干扰档指标 / baseline 指标`。

## 6. 三边实现等价性检查清单

提交前逐条核对：

- [ ] `checksum256` 用 u32 回绕，三边一致（不可用 64 位中间量）
- [ ] `h` 用 i32 回绕，Rust 侧显式 `wrapping_*`
- [ ] 解析手写扫描，三边都不用标准库 `atoi`/`strtol`
- [ ] S4 真的在堆上分配、真的释放
- [ ] 响应 hex8 小写、补前导 0
- [ ] 长连接串行处理（不 pipeline 多请求）
- [ ] 三边 worker 数一致（见 §7）
- [ ] 三边都不开额外日志/打点到热路径

## 7. 线程/Worker 配置

服务端并发度必须显式设定且三边一致，否则测的是配置差异不是运行时差异。

| 运行时 | 配置方式 |
|---|---|
| Kaula | `kaula_runtime_init` 的 `worker_count`（kl 侧通过 `init_ctor` 预热固定） |
| Go | `GOMAXPROCS` |
| Tokio | `worker_threads`（`#[tokio::main]` 前显式 `Builder`） |

**默认取 4**（与历史 `service/` 基准一致），并在报告中注明；
干扰档下保持同一配置，只改变外部压力。
