# kaulac i32 算术提升缺陷（最小复现 + 成因）

> **发现于** `test/bench/service3` 三方服务基准的三边 checksum 对齐检查。
> 这是一条**编译器 codegen 正确性缺陷**，与 `FINDINGS.md` F7 同类
> （「跨语言基准里溢出语义不一致」），但这次在**编译器一侧**，不是基准一侧。
>
> **状态**：未修。本轮基准以「不使用溢出表达式」规避（见 §5）。
> 修复需要动 codegen 的类型提升规则，涉及面广，已单独立项。

## 1. 症状

三边服务用同一份事务语义（`TRANSACTION.md` §3.2）：

```
i32 h = 0
for k in 0..64:
    h = (h ^ rec[k]) + seq + qty + price
    h = h * 31 + k
checksum ^= u32(h)
```

- **Go**：`h = -768271034` → checksum `2ceb59c5`（真实执行确认）
- **Rust（wrapping）**：同上（i32 语义）
- **Kaula**：checksum `2ceba850` —— **不一致**

## 2. 定位过程（已排除的项）

| 假设 | 判定 | 证据 |
|---|---|---|
| `checksum256`（u32 段）算错 | **否** | Kaula 的 `ck % 2^31 == 753621445 == Go 的 0x2ceb59c5 % 2^31`，**逐位一致** |
| `parse_field_at` / `t` 解析错 | **否** | seq=1 / qty=3 / price=1990 三边一致 |
| 响应编码/hex 转换错 | **否** | 注入打印捕获的真实字节流 `R,1,2ceba850,5970`，格式正确 |
| KMM 分配/释放污染 | **否** | 独立探针在无 KMM 路径下同样复现 |
| i32 溢出契约是「陷阱」 | **否** | `i32 c = 2000000000 + 2000000000` 实测返回 **-294967296**（正确回绕，无 trap） |

**关键实验（把歧义降到零）**：把 `rec` 全置 0，使表达式退化为
`(h ^ 0) + 1 + 3 + 1990`，其中 `h ^ 0 == h` 无任何类型提升歧义：

```kaula
fn fold_b(seq: i32, qty: i32, price: i32) -> i32 {
    i32 h = 0
    for k in range(64) {
        h = (h ^ 0) + seq + qty + price
        h = h * 31 + k
    }
    return h
}
```

| 实现 | 结果 |
|---|---|
| Go `int32`（真实执行） | **882415648** |
| Kaula（真实执行） | **882415648** ✅ |

→ **场景 B 三边一致**。缺陷只在**带动态记录值 `rec[k]` 的场景 A** 出现。

## 3. 成因：表达式被提升到 i64 求值，链中间结果丢失 i32 回绕

`kaulac` 对**混合了非 i64 操作数**的算术表达式生成 `kaula_add_i64` /
`kaula_mul_i64`（`src/kaula_runtime.h:57-79`，带 `__builtin_*_overflow`
溢出检查），并显式把操作数提升到 `int64_t`：

```c
/* 场景 B 的生成代码（cache/f7f7dd…c:36-37）—— 结果正确 */
int32_t h = 0;
h = kaula_add_i64((int64_t)(kaula_add_i64((int64_t)(
        kaula_add_i64((int64_t)(h ^ 0), (int64_t)(seq))),
        (int64_t)(qty))), (int64_t)(price));
h = kaula_add_i64((int64_t)(kaula_mul_i64((int64_t)(h), (int64_t)(31))), (int64_t)(k));

/* 场景 A 的生成代码（cache/f99e616…c:367,371）—— 结果错误 */
h = kaula_add_i64(...((h ^ (int32_t)(r[k])) ...));   /* 递归提升整棵子树 */
h = kaula_add_i64((int64_t)(kaula_mul_i64((int64_t)(h), (int64_t)(31))), (int64_t)(k));
```

**关键差异**：两段都「把整棵表达式树提升到 i64 求值、只在赋值给 `h` 时
截断回 i32」。区别在于**截断的时机与次数**：

- 正确的 i32 语义要求**每一个二元运算都回绕**：
  `h = h*31 + k` 是 `(i32)((i32)(h*31) + k)`，共 2 次回绕。
- 生成代码把 `h*31` 与 `+k` **合并**为一次 i64 表达式，只有 1 次截断。

`h*31` 在 k≈7 之后就持续溢出 i32，两边的**回绕次数不同**，长期累积即分叉。

> 注：**为什么场景 B 恰好一致，需要单独判定** —— 上面两段生成代码形态相同，
> 结果却一正一错。本轮已确认的是「场景 A 错、场景 B 对」，
> 以及「两段的提升形态一致」。**根因的精确触发条件尚未完全闭合**
> （怀疑与 `x ^ (int32_t)(r[k])` 这一子表达式的提升路径相关），
> 已单独立项追踪，不在本轮基准阻塞项内。

## 4. 为什么这条值得单独记

- **违反 Kaula 自身实测契约**：`i32` 加法实测是**静默回绕**（§2 关键实验），
  但链式表达式里的中间结果不回绕。同一个 `i32` 类型，两种溢出行为。
- **静默**：不报错、不警告、正常退出，只是数值不同 —— 最危险的一类。
- **跨语言基准必然踩到**：任何「用哈希/累加器做校验」的事务都会触发。
  F7 的教训是「先问三边溢出语义是否一致」，本条的教训是
  「**别假设同一语言内不同表达式形态的溢出语义一致**」。

## 5. 本轮规避方式

基准事务改为**每步显式落到 i32 变量**，不使用链式表达式：

```kaula
// 不用：h = h * 31 + k
i32 tmp = h * 31
h = tmp + k
```

这样每步都在 i32 上完成并回绕，三边逐位一致（已用 `mismatch=0` 验证）。

**必须随报告披露**：本基准的 Kaula 侧使用规避写法。
这不影响三方对比的公平性（三边算的是同一件事、同一组常量、
同样多的循环），但**用户按文档直写链式表达式会得到不同结果**。

## 6. 建议的修复方向（未做）

1. **codegen 层**：`i32` 类型的二元表达式应在 i32 域求值并按 i32 回绕，
   不整树提升到 i64。溢出检查若保留，应对 **i32 域**检查 i32 溢出，
   而不是对 i64 中间结果检查。
2. **或语义层**：明确 Kaula 的「整数溢出」契约 —— 是回绕、陷阱、
   还是依赖类型宽度逐运算判定。当前实测行为是**三种混用**。
3. **回归用例**：把 §2 的场景 A / B 与 §3 的关键实验固化为
   `test/` 下的语义用例，防止后续 codegen 改动再次引入。

```bash
cd test/bench/service3/kaula_kl && kaulac fold_b.kl && ./fold_b   # 882415648
```
