# Kaula conc vs Go —— 每秒 6 万请求定速对比报告

> **被测问题**：同一份真实混合服务负载（`TRANSACTION.md` §3），
> **固定每秒 60,000 请求**的开环压下，Kaula conc 与 Go 两个服务的
> **TPS 与尾延迟（P50/P95/P99/P999）**哪个更好？
>
> 与 `REPORT.md`（闭环、并发连接即负载）的区别：本轮是**定速开环**——
> 客户端按时刻表恒速发送 60,000 req/s，服务跟不上时会表现为
> ok 掉队 / 尾延迟上涨，而不是客户端自发减载。
> **「每秒 6 万请求下」因此是一个受控的输入，而不是测得的结果。**

测量环境：Linux x86_64，**32 核**（压测期间机器 ~90% 空闲），
clang 18.1.3，kaulac v1.1.1（go1.27.2 构建），Go 服务端 go1.27.2 构建，
loopback，压测器与被测服务同机（RTT 含完整协议栈，两边口径一致）。

---

## 1. 被测对象与同配置口径

| 边 | 实现 | worker/线程数 | 构建 |
|---|---|---|---|
| **Kaula conc** | `kaula_kl/order_server.kl`（`conc fn conn_task` + `spawn`，经 kaulac 编译） | `SVC_WORKERS=4`（运行时 worker） | kaulac v1.1.1 + clang 18.1.3 |
| **Go GMP** | `go/order_server.go`（goroutine per conn + bufio） | `GOMAXPROCS=4` | go1.27.2 |

- **负载事务**：`O,<seq>,itemA,3,1990` → `R,<seq>,<hex8>,<total>`，
  每请求五段流水线（checksum256 计算 + 解析 + 堆分配 64B 混合校验
  + `sleep(200µs)` 模拟下游 IO + 编码响应），两边逐位等价。
- **正确性前置**：压测器独立复刻服务端算法，逐响应校验
  格式/seq/hex8/total 四项。**10/10 轮全部 `mismatch=0 errors=0`**——
  任何一边算错，该轮作废不出数字。
- **同配置**：worker 数 4=4；并发连接 1024=1024；同一个压测器二进制；
  同一个 `loadgen` 定速调度器（见 §5）。

## 2. 结果（5 轮交错，收敛段中位数）

每轮 30s（+3s 预热不计入），5s 一窗共 6 窗，**丢弃前 50% 窗口**
（预热+爬坡）后取中位；三方轮转交错执行（kaula→go→kaula→go…），
消除「时间序」混入「运行时」差异。下表为**跨轮中位数**（括号内为跨轮极差）：

| 指标 | **Kaula conc** | **Go GMP** | 胜方（中位比） |
|---|---:|---:|---|
| **TPS** | **60,162**（60,161~60,170） | **60,187**（60,177~60,192） | 平（都在给定负载上限） |
| **p50** | **282 µs**（280~283） | 430 µs（386~444） | **Kaula 快 1.52×** |
| p95 | **397 µs**（394~405） | 1,410 µs（1,397~1,414） | **Kaula 快 3.55×** |
| **p99** | **929 µs**（620~1,890） | 1,629 µs（1,504~1,720） | **Kaula 快 1.75×** |
| **p999** | 7,375 µs（4,090~17,768） | **4,433 µs**（4,251~4,902） | **Go 快 1.66×** |
| 客户端实际发送（offered/s） | 60,212 | 60,240 | 标称 60,000 + 0.4% 调度追赶 |
| 轮内离散度 spread(TPS) | ≤0.3% | ≤0.3% | 两边都收敛 |
| 有效轮数 | 5/5 | 5/5 | — |

> **读法**：TPS 打平**不是**「两个服务一样快」——60k/s 是客户端
> 给定的负载，两边都扛住了（ok≈offered，errors=0），TPS 到达
> 天花板失去分辨力。**真正的分辨力在延迟分位**：Kaula 赢在中段
> 与近尾（p50/p95/p99），Go 赢在深尾（p999）。

### 2.1 每轮明细（µs）

| 轮次 | kaula p50/p95/p99/p999 | go p50/p95/p99/p999 |
|---|---|---|
| 1 | 282 / 394 / 620 / 4,090 | 412 / 1,408 / 1,629 / 4,418 |
| 2 | 281 / 397 / 929 / 7,375 | 434 / 1,413 / 1,720 / 4,720 |
| 3 | 283 / 397 / 923 / 4,943 | 444 / 1,410 / 1,530 / 4,433 |
| 4 | 280 / 404 / 1,859 / 9,975 | 386 / 1,397 / 1,504 / 4,902 |
| 5 | 282 / 405 / 1,890 / 17,768 | 430 / 1,414 / 1,632 / 4,251 |

p50/p95 上 Kaula **5:0 全胜**（极差不重叠，结论稳固）；
p99 上 Kaula 中位快 1.75× 但第 4/5 轮被 Go 反超（跨轮波动大）；
p999 上 Go 中位快 1.66× 且**跨轮极稳**（4,251~4,902），
Kaula 的 p999 跨轮波动 4.1ms~17.8mm——**深尾稳定性是 Go 的明确优势**。

## 3. 根因分析

### 3.1 Kaula 为什么中段快：200µs 睡眠的定时器精度

负载里每个请求有一次 `sleep(200µs)`，p50 基本被它定义：

- **Kaula**：CONC 的 IoDriver 持 ns 精度最小堆定时器
  （`DESIGN_CONC_VS_GMP_VS_TOKIO.md` §3.1），睡眠实测 ~282µs
  ≈ 200µs + ~80µs（五段计算+IO）。
- **Go**：`time.Sleep` 走运行时定时器（µs 精度四叉堆），
  本仓 `FINDINGS.md` F2 实测 200µs 睡眠 **p50 超额 3.1×**
  （623µs）——430µs ≈ 200µs + 定时器超额 + 计算。
- p95 的 3.55× 差距同源：Go 侧绝大多数睡眠都吃到了超额，
  Kaula 侧只有少数吃满。

### 3.2 Go 为什么深尾快：单 IoDriver vs 分布式 netpoller

6 万请求/秒 = 每秒 6 万次睡眠定时器插入/到期 + 12 万次
recv/send epoll 事件，**全部汇入 CONC 的单个 IoDriver 线程**。
负载均衡时它跟得上（中段赢），但单点的队列ing 抖动直接体现为
p999 尖峰（跨轮最大 17.8ms）。Go 的 netpoller 与 per-P 定时器
是分布式结构，没有这个单点，p999 稳定在 4.3~4.9ms。

> 这与 `REPORT.md` 的结论不矛盾：那边是闭环满载（TPS 54.8k vs
> 78.5k，Kaula 先饱和），两边都在拼吞吐；本轮是定速 6 万
> （低于两边饱和点），拼的是延迟分位——**问题的问法决定了
> 谁的架构优势可见**。

## 4. 过程中发现：kaulac 的 KMM scope 泄漏（连接 churn → 服务 abort）

定速压测首轮用 4096 连接时，Kaula 服务在**压测结束、连接潮汐
关闭时** `SIGABRT`：

```
KMM FATAL: Scope stack overflow (depth 1024 >= max 1024), aborting
```

定位为 **kaulac 代码生成缺陷**：`conc fn` 内 KMM scope 中的提前
`return`（`conn_task` 的 `got<=0` 连接关闭路径）不弹作用域栈，
每次连接关闭在所在 worker 线程的 TLS 栈上泄漏一帧；4096 连接 ÷
4 worker = 1024 次关闭/线程，恰爆上限。完整证据链、复现与修复
建议见 **[`KBUG_KMM_SCOPE_EARLY_RETURN.md`](KBUG_KMM_SCOPE_EARLY_RETURN.md)**。

**对基准的影响与处置**：连接数降至 1024（潮汐关闭时每线程
≤256 次泄漏，不触上限）后复测，10/10 轮 `errors=0`。
这是**规避不是修复**——长周期运行的服务关闭次数累计超限仍会崩，
真修复需改 codegen（KBUG §6）。

## 5. 复现

```bash
# 0) 工具链（kaulac v1.1.1 + 运行时）
python toolkit_build.py --release

# 1) 构建两边服务与压测器
cd test/bench/service3
kaulac kaula_kl/order_server.kl \
  -cflags "kaula_kl/svc_wrap.c -I<repo>/src/concurrency -I<repo>/build/include"
(cd go && go build -o order_server_go .)
go build -o /tmp/svc3/loadgen ./loadgen.go

# 2) 定速 6 万请求/秒，5 轮交错（--rate 为新增开环模式，缺省为原闭环）
python3 run_service3.py --only kaula,go --levels baseline \
    --conns 1024 --sec 30 --win 5 --rounds 5 --rate 60000 \
    --out results_60k.json
```

定速实现（`loadgen.go`）：**序列调度**——第 i 个请求的发送时刻为
`start + i/rate`，各连接 goroutine 发前各自睡到时刻。精度不依赖
单线程（初版令牌桶在千级 goroutine 下被调度饿饿丢 tick，offered
只有标称 55%~70%，已弃用）；`offered`（实际发送数）与 `ok` 的
差值即「服务扛不住」的直接证据。窗口行输出格式
`win,tps,p50,p95,p99,p999,mismatch,errors` 与原版一致，
TOTAL 行新增 `offered/err_eof/err_timeout` 分类计数。

## 6. 结论

**在每秒 6 万请求的定速压下，两个服务都扛住了负载（TPS 打平、
mismatch=0、errors=0），好坏取决于你关心哪一段延迟：**

| 关心的问题 | 更好的服务 | 数据 |
|---|---|---|
| 典型延迟 / 近尾（p50/p95/p99） | **Kaula conc** | 快 1.5×~3.6×，5:0 全胜 |
| 深尾延迟 / 深尾稳定性（p999） | **Go GMP** | 中位快 1.66×，且跨轮极稳 |
| 吞吐上限 | 平（均未触顶，6 万低于两边饱和点） | 60,162 vs 60,187 |

- **选 Kaula conc**：负载以「中低延迟敏感」为主（如每次请求都有
  短下游等待的场景），其 ns 精度定时器在 200µs 级睡眠上优势明确。
- **选 Go**：SLA 盯 p999/最大延迟，或不能接受深尾抖动——
  Go 的分布式 netpoller/定时器没有单 IoDriver 这个尾部单点。
- **两者都要注意**：Kaula 边的 `KMM scope 泄漏`（KBUG）在连接
  churn 场景是可用性风险，修复前不建议长周期生产运行。

## 7. 可比性限制（披露）

1. 压测器与被测服务同机（loopback），RTT 含双方调度争抢；
   但三边口径完全一致，且机器 ~90% 空闲，争抢可忽略。
2. Go 服务端由 go1.27.2 构建（`REPORT.md` 历史数据为 go1.25.0），
   版本差异未做对照实验。
3. Kaula 侧 p99/p999 跨轮波动明显大于 Go（见 §2.1），
   深尾结论按「中位数 + 跨轮稳定性」双口径读。
4. 本报告只跑 baseline（无干扰档）；抗干扰退化曲线见 `REPORT.md`。
