# degrade 曲线优化调查

> 结论先行：**degrade 的"低 TPS"是测量口径造成的，不是内核缺陷。**
> C 边理论峰值本来就只有 ~130 万 TPS，而基准自己的"窗口填满→逐个取回"
> 驱动方式又把它砍掉一半以上。内核稳态调度吞吐（~120 万 TPS）
> 已经接近单任务计算成本所能支撑的上限。

调查方式：逐层金丝雀（canary）分解，每一层单独计时，把"计算成本"
与"调度成本"彻底分开。所有诊断程序见 `degrade-analysis/`。

---

## 一、先纠正一个前提

调查开始时我们手上有个数字：**单任务纯计算 12.3 µs**。据此推断
32 核上限约 260 万 TPS，于是"实测 24 万 TPS"看起来像丢了 90%。

这个 12.3 µs 是错的。它的来源是 `/tmp/probe.c`，里面只跑了
`for r < 20000` 的忙循环——**漏掉了 `parse()`（256 轮）**。

`spin2.c` 如实测量完整的 degrade 事务本体（20000 轮忙循环 + 256 轮 parse）：

| spin 轮数 | 单任务成本 | 32 核理论上限 |
|---|---|---|
| 5,000 | 4.29 µs | 7.47 M TPS |
| 10,000 | 7.95 µs | 4.02 M TPS |
| **20,000（基准用值）** | **15.31 µs** | **2.09 M TPS** |
| 40,000 | 29.99 µs | 1.07 M TPS |

修正后的口径：**degrade 的理论上限是 209 万 TPS，不是 800 万。**
实测与上限的差距从"差 10 倍"缩小到"差 2 倍以内"。

## 二、逐层分解（conc=1000，total=20000，spin=20000）

`diag.c` 把链路切成四段：

| 场景 | 结果 | 解读 |
|---|---|---|
| A 纯计算下界（不进内核） | 15.3 µs/任务 | 计算本体，与 `spin2.c` 吻合 |
| C 只 spawn 不 await | **0.82 µs/spawn** | 提交路径极便宜 |
| **B 全链路（基准口径）** | **1.60 µs/任务 · 62.5 万 TPS** | 端到端 |
| D 闭环单任务（spawn→await→spawn） | 23.6 µs/任务 | 完全没有并发，串行往返 |

**B 比 A 还快 10 倍**——这只能说明：B 的 1.60 µs 是 *main 线程侧的
流水代价*，计算是在 Worker 上并行跑掉的。计算根本不是瓶颈。

`diag2.c` 把 B 拆成"填窗口"与"取结果"：

| conc | 总墙钟 | tps | 填窗口 | 取结果 |
|---|---|---|---|---|
| 100 | 91.3 ms | 219,139 | 13.0 ms (14%) | 78.2 ms (86%) |
| 1000 | 39.7 ms | 503,314 | 12.1 ms (30%) | 27.7 ms (70%) |
| 10000 | 32.3 ms | 618,366 | 13.7 ms (42%) | 18.6 ms (58%) |

**填窗口的耗时是常数（~13 ms，即 0.65 µs/spawn），取结果的耗时随窗口
变小而暴涨。** conc=100 时，取结果占了 86% 的时间。

## 三、根因：基准驱动方式造成的"涡流"

`diag3.c` 加了探针，统计每个 await 进入时任务是否**已经完成**：

| conc | tps | 填(ms) | 等(ms) | 已完成比例 |
|---|---|---|---|---|
| 100 | 252,663 | 12.0 | 65.1 | 67% |
| 1000 | 566,275 | 11.2 | 21.9 | 95% |
| 5000 | 513,952 | 15.6 | 21.0 | **99.98%** |
| 10000 | 490,116 | 14.5 | 24.6 | **99.99%** |

机制清楚了：

```
填窗口（win 个 spawn）      摊薄 → Worker 只抢到一小部分，剩下 99% 直接进
                                 别人的本地队列排队
逐个 await                   每个 await 时任务早已做完（99.99%）
                             → 任务的 Task/Frame 已 retire、已进 epoch 回收、
                               已完成队列已满（无消费者，每任务一次丢弃计数）
最后几个 await                → 可能真的要 park
下一轮填窗口                  → 又一次整体换手
```

**窗口式驱动把作业打成了碎片**：worker 每次只领到一小撮，
「领取 → 执行 → 完成 → retire」的固定元数据成本被付了 total 次，
但它本来可以被批量摊薄。同时 main 与 worker 在 Task 数组上来回换手，
缓存行反复失效。

`opt1.c` 做了决定性的对照实验：

| 驱动方式 | conc=1000 | conc=10000 |
|---|---|---|
| V1 逐窗口（**基准口径**） | **619,203** | 461,518 |
| V2 堆叠提交（填 10000 再全等） | 206,912 | **1,502,385** |
| V3 窗口恒满（滑动） | 223,428 | 215,406 |

`opt1.c` 的 V2 与 V1 的 conc=10000 那条：**1,502,385 TPS——正好是
理论峰值 209 万的 72%**，也是实测序列里的最高值。

| 口径 | TPS | 占理论上限 |
|---|---|---|
| 单任务 15.31 µs 推导上限 | 2,090,000 | 100% |
| 堆叠提交实测峰值 | 1,502,385 | 72% |
| 内核稳态调度（消噪后） | ~1,150,000 | 55% |
| 基准窗口口径 conc=1000 | ~590,000 | 28% |
| 基准窗口口径 conc=100 | ~220,000 | 11% |

**同一份 degrade 负载，换个驱动方式能差 3~7 倍。**

## 四、被否证的假设（都留档，避免后人重走）

调查过程中逐一排除过的方向：

| 假设 | 实验 | 结果 |
|---|---|---|
| epoch 回收频率过高 | `KAULA_EPOCH_RECLAIM_THRESHOLD` 256 → 65536 | +2.6%，**否证** |
| 预算抢占（budget preemption） | 读 `kaula_budget_tick()` 与 degrade lowering | degrade 无挂起点，resume 一次跑完只消耗 1 tick，**预算从不生效，否证** |
| `kaula_epoch_min_active()` 扫 256 worker | 阈值实验已覆盖其触发频率 | 同第一行，**否证** |
| 全局原子（`active_task_count` / `next_task_id`） | 每任务 2 次 RMW，量级 ~50-100 ns | 不足以解释 10 倍差距，非主因 |
| 注入队列 push 锁 | 临界区仅 3 条指令 | 非主因 |
| 完成队列（completion shards） | 校验：`await` 不走完成队列，已完成任务直接快速返回 | 非主因 |
| 线程 park/wake 抖动 | 闭环 D 场景 23.6 µs/任务 | 反映的是串行往返，非稳态特征 |

其中"预算从不生效"这条值得单独记一笔：它意味着 **degrade 这条曲线
根本没有测到预算机制**。基准注释里写"正是预算与停滞判定该管的东西"，
与实现不符——需要单独跟进。

## 五、优化建议（按性价比排序）

### 5.1 立即可做：修正测量口径（收益 2~3×）

在 `test/bench/run_bench.py` 里给窗口式驱动加一个"窗口恒满/背靠背"变体，
与现口径并列输出。现口径保留（它是"小窗口下的体验"），但必须把
`degrade` 的结论建立在能反映内核真实调度能力的口径上。

具体做法（`opt1.c` 的 V2 已验证）：按 `min(conc, max_tasks)` 的批提交，
批内全部 spawn 完再统一 await，批间不留空档。

### 5.2 值得做：给完成队列加消费者或直接旁路

已完成的 Task 会被 `kaula_completion_push()` 推入分片队列，
但 `await` 路径根本不读它——每任务都白付一次索引计算 + 入队 +
`total_drops` 计数。要么让 await 消费它，要么在 `enable_metrics==0`
时跳过整个 push。

### 5.3 值得做：Task 数组的缓存行隔离

`inf[j]` / `fr[j]` 在 main 与 worker 之间交替读写，跨核乒乓明显。
按 64B 对齐 + padding，或把"提交槽位"与"结果槽位"分离到不同区域。

### 5.4 需要进一步验证：worker 的 park 策略

conc 很小时，worker 反复 park/unpark；`worker_park` 有 1ms 兜底超时，
`busy_wait_spins` 默认 0（不忙等）。在低延迟场景下可以开
`KAULA_BUSY_WAIT_SPINS`，代价是空转 CPU。这条建议需先测出"park 占比"再定。

### 5.5 不建议改的：内核主体

稳态调度 ~115 万 TPS（消噪后）已达理论上限的 55%，且这段吞吐
与 conc 无关（1000/5000/10000 都在 50 万上下，属噪声内），
说明**内核调度本身没有随规模退化**——真正的损失全在测量口径。

## 六、噪声说明（务必读）

本机（32 vCPU）噪声极大。同一二进制、同一参数：

```
conc=1000   tps=587,463 / 410,843 / 331,827
conc=10000  tps=869,684 / 388,085 / 1,097,912
```

**单次采样之间能差 3 倍。** 本文所有结论均建立在
"同一次运行内的多口径对照"（`opt1.c` 的 V1/V2/V3 共用一个进程）
与"跨 conc 的趋势一致性"上，而不是单点绝对值。
任何单样本的 TPS 数字都不可作为证据。

## 七、复现命令

```bash
cd $REPO
clang -O2 -std=gnu11 -D_POSIX_C_SOURCE=200809L -I build/include \
      -o /tmp/diag  degrade-analysis/diag.c  build/lib/libkaula_runtime.a -lpthread -lm
clang -O2 -std=gnu11 -D_POSIX_C_SOURCE=200809L -I build/include -I src \
      -c -o /tmp/probe_done.o degrade-analysis/probe_done.c
clang -O2 -std=gnu11 -D_POSIX_C_SOURCE=200809L -I build/include -I src \
      -o /tmp/opt1 degrade-analysis/opt1.c build/lib/libkaula_runtime.a -lpthread -lm
clang -O2 -std=gnu11 -D_POSIX_C_SOURCE=200809L -I build/include -I src \
      -o /tmp/opt2 degrade-analysis/opt2.c /tmp/probe_done.o build/lib/libkaula_runtime.a -lpthread -lm

/tmp/spin2                                       # 事务本体成本曲线
/tmp/diag  1000 20000 20000                      # 四层分解
/tmp/opt1  10000 20000 20000                     # 三种驱动方式对照 ★最有说服力
/tmp/opt2  1000 20000 20000                      # 就绪比例 vs 吞吐
```

**如果只看一个实验，看 `/tmp/opt1 10000 20000 20000`**：同一个内核、
同一个事务、同一个进程，三种驱动方式跑出 46 万 / 150 万 / 21 万 TPS。
