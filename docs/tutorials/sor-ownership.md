# SOR Sub-structural Ownership

SOR（Sub-structural Ownership）是 Kaula 的**编译期**所有权与内存安全分析，
追踪每个资源的唯一所有权，在编译期消除数据竞争和悬垂指针，**零运行时开销**。

> 启用方式：编译命令行加全局标志 `kaulac --sor main.kl`。
> SOR 是**自动**分析——你写的业务代码不需要任何特殊关键字，编译器在语义分析阶段
> 自动推断每个对象的所有权状态并报告违规。

## 它对普通程序做什么

下面这段普通 Kaula 代码，加不加 `--sor` 都能编译运行；加了 `--sor` 后，编译器
会额外做一遍所有权检查（比如同一块内存被两个可变别名同时借用、或被 use 两次）：

```kaula
import std.io
import std.memory

fn main() {
    // KMM V4 在作用域退出时批量回收，SOR 在此之上再做编译期别名/逃逸检查
    i64* p = as<i64*>(std.memory.kmm_v4_alloc(64))
    p[0] = 100
    p[1] = 200
    println("sum = ", p[0] + p[1])
}
```

编译：

```sh
kaulac --sor main.kl
```

> 当前 SOR 是分析与报错层，不改变生成的 C 代码形态；它只在 `--sor` 开启时
> 把所有权问题作为编译错误报出。

## 设计上的三大所有权原语（背景）

SOR 的分析模型基于三个概念（详见 [SOR 系统实现](../sor-system.md)）：

| 原语 | 含义 | 代码里如何体现 |
|------|------|----------------|
| **yield**（转移/move） | 资源唯一所有权从一个变量转到另一个，原变量失效 | 函数传参、返回值按 move 语义传递 |
| **release**（共享只读） | 把只读访问权分发出去，允许多个读者 | 只读借用、不可变引用 |
| **extract**（提取） | 从复合结构中取出某子项的所有权 | 容器元素取出后原位置留空 |

这些是分析引擎内部的状态机（`Owned / Released / Extracted / Moved / Hollow`），
不是你要手写的语句。你只要像平时一样写代码，SOR 在 `--sor` 模式下判定是否违反
了"同一时刻只有一个可变写者"的规则。

## 字段写穿不是 yield——但它同样延命

这是所有权模型里最容易混淆的一处，单独说明：

```kaula
Node* l = mk(depth - 1)   // l：局部变量，Owned
Node* n = as<Node*>(std.memory.kmm_v4_alloc(16))
n.left = l                // 字段写穿——不是 yield(l)
```

`yield` 是**用户显式**的所有权转移：交出所有权，原变量失效。
`n.left = l` 什么原语都不是——`l` 没有交出所有权，它只是往 `n` 的字段里
**存了一个指针值**。但这个存储动作产生了一个**随宿主 `n` 存活的字段引用**：
`n` 活多久，`n.left` 里的地址就可读多久。

SOR 的 liveness 因此必须按「**所有引用（含字段引用）都消亡**」判定对象死亡，
而不是按「局部变量的词法最后使用点」。否则会在写穿点回收 `l` 指向的对象，
而 `n.left` 仍在读它 → 悬垂。编译器对写穿源对象的处理（豁免 early free
与 return 回收、死亡点推迟到宿主）就是这条规则的落地——你不需要写任何
额外关键字。

一个直接后果：宿主逃逸时（`n.left = l; ...; return n`）字段引用最长命，
保活需求最强。这类跨函数返回的聚合结构（如递归建树）在 Kaula 的内存模型下
由 survivor 段承载，其回收限制见
[核心运行时 · KMM 已知限制](../core-runtime.md#210-已知限制)。

## 调试 SOR 报错

当 `--sor` 报告所有权违规时：

- 错误信息会指向具体的变量与行号；
- 常见原因：把同一块内存的可变别名传给了两条独立执行路径（线程逃逸）、
  或在资源已经 move 之后再次使用；
- 修正方式通常是缩短资源作用域、或把需要共享的数据改成只读传递。
